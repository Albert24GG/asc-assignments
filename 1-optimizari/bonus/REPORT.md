# Ice Lake Analysis

## Scope

This directory contains the same algorithm implemented for an Intel Xeon Gold 6326, based on the Ice Lake microarchitecture:

- `solver_neopt.c`
- `solver_neopt_equiv.c`
- `solver_opt.c`
- `solver_blas.c`

Unlike the Haswell analysis, this one does not include cachegrind. The optimized binary is compiled with `-march=native` and uses AVX-512, which prevents valgrind/cachegrind from running correctly. As requested, the analysis therefore focuses on benchmark runtimes and explains the observed differences using the code changes and the architectural characteristics of Ice Lake.

The benchmark methodology is unchanged from the main project:

```bash
<bench_program> -n <N> -s 1234 -w 10 -t 30 -a 16
```

All comparisons use the `mean` runtime from the CSV benchmark tables.

The plots for this report are generated by:

- `graphs/generate_graphs.py`

which writes the SVG files in `bonus/graphs/`.

## Ice Lake architecture

Tested CPU:

- Model: Intel(R) Xeon(R) Gold 6326 CPU @ 2.90GHz
- Architecture: Ice Lake
- Base frequency: 2.90 GHz
- Boost frequency: 3.50 GHz
- Sockets: 2
- Cores per socket: 16
- Threads per core: 2
- L1d cache: 48 KB per core
- L1i cache: 32 KB per core
- L2 cache: 1.3 MB per core
- L3 cache: 24 MB shared per socket

Relative to the Haswell machine used in the main project, the most important differences for this assignment are:

- AVX-512 support instead of AVX2,
- larger L1 data cache,
- much larger private L2 cache,
- newer core with generally stronger vector throughput.

These matter most for the optimized version, because the naive scalar versions are still dominated by the same cubic loop nests and poor locality patterns.

## Code changes in `solver_opt.c`

The Ice Lake optimized implementation keeps the same high-level structure as the Haswell `opt_avx` version:

- blocked `A^T * B`,
- distributive rewrite for the final accumulation,
- packed storage of only the upper triangle of `D`,
- vectorized helper kernels for dot product, AXPY, and vector addition.

The architecture-specific changes are the following.

### 1. Block size increased from 32 to 40

The code now uses:

```c
#define BLOCK_SIZE 40
```

This matches the larger 48 KB L1 data cache. Using the same estimate as in the Haswell report,

```text
sqrt(48 KB / (3 * 8 B)) = 45.25
```

and rounding down to a multiple of 8 gives a practical block size of `40`. This lets each working tile use more of L1 before spilling into lower cache levels.

### 2. AVX-512 replaces AVX2

The hot kernels now operate on `__m512d`, so each vector register holds 8 doubles instead of 4:

- `vec_dot` uses `_mm512_fmadd_pd`,
- `vec_axpy` uses `_mm512_fmadd_pd`,
- `vec_add` uses `_mm512_add_pd`.

This doubles the useful data width per vector instruction relative to the Haswell AVX2 version. In principle that creates room for almost a `2x` arithmetic throughput gain in the best-case vector loops, although the full solver cannot realize that ideal because it still performs the same memory traffic and still contains scalar control code around the vector kernels.

### 3. Stronger alignment discipline

The Ice Lake version aligns the working allocation to 64 bytes and copies the input matrices `A` and `B` into aligned buffers:

- `posix_memalign(..., 64, ...)`
- aligned `_mm512_load_pd` and `_mm512_store_pd`

This is a meaningful change compared with the Haswell code, which used unaligned loads/stores. With 512-bit vectors, a misaligned access is more likely to cross cache-line boundaries, so alignment matters more. The explicit copy of `A` and `B` is an extra upfront cost, but for these matrix sizes the cost is negligible compared with the cubic work that follows.

### 4. Memory reuse remains aggressive

The code still reuses the large aligned allocation carefully:

- one region for aligned copies of `A` and `B`,
- one region for `C`,
- then the memory previously used by `A` and `B` is reclaimed for `D`.

This keeps the working set compact and avoids extra allocations of full-size matrices.

## Ice Lake benchmark results

The four measured versions are:

- `blas`
- `neopt`
- `neopt_equiv`
- `opt`

Graph:

- [Ice Lake runtime comparison](graphs/runtime_ice_lake.svg)

At `N=1400`, the mean runtimes are:

- `blas`: `0.534 s`
- `opt`: `1.011 s`
- `neopt_equiv`: `12.007 s`
- `neopt`: `24.853 s`

The ranking is stable for all tested sizes:

```text
BLAS < opt < neopt_equiv < neopt
```

### `neopt` vs `neopt_equiv`

The difference between the two unoptimized versions is almost exactly the same as on Haswell: `neopt_equiv` removes the repeated symmetric matrix-vector products by regrouping them into a single multiplication by the row sum of `C`.

On Ice Lake this gives:

- `2.02x` speedup at `N=400`
- `2.06x` speedup at `N=1000`
- `2.07x` speedup at `N=1400`

This is expected because the change is algorithmic at the loop-structure level. It reduces redundant work regardless of microarchitecture.

### `opt` vs `neopt_equiv`

The optimized Ice Lake version is much faster than the fair baseline:

- `14.32x` at `N=400`
- `11.89x` at `N=1000`
- `11.87x` at `N=1400`

This gain comes from combining several effects:

- blocked multiplication improves locality,
- the larger Ice Lake L1 and L2 caches support larger tiles,
- AVX-512 doubles vector width relative to the Haswell AVX2 implementation,
- 64-byte alignment lets the code use aligned vector loads/stores cleanly,
- the packed symmetric representation of `D` still cuts memory footprint substantially.

The speedup is larger at small `N` because the optimized version has less loop and call overhead, and the entire working set fits more comfortably in the cache hierarchy. At larger `N`, the cubic matrix operations increasingly dominate and the gains stabilize around `12x`.

### `opt` vs `blas`

BLAS is still the fastest implementation:

- `2.19x` faster than `opt` at `N=400`
- `1.88x` faster at `N=1000`
- `1.89x` faster at `N=1400`

That is not surprising. Even though `opt` uses AVX-512 and a reasonable block size, vendor-tuned BLAS kernels still benefit from more refined packing strategies, better micro-kernel scheduling, and deeper architecture-specific tuning than a course assignment implementation.

## Haswell vs Ice Lake

For the cross-architecture comparison, I used the benchmark results from the main project for Haswell and the benchmark results from `bonus/results/` for Ice Lake. All four comparisons use only the matching sizes:

```text
N = 400, 600, 800, 1000, 1200, 1400
```

The plots are:

- [BLAS: Haswell vs Ice Lake](graphs/arch_compare_blas.svg)
- [neopt: Haswell vs Ice Lake](graphs/arch_compare_neopt.svg)
- [neopt_equiv: Haswell vs Ice Lake](graphs/arch_compare_neopt_equiv.svg)
- [opt: Haswell vs Ice Lake](graphs/arch_compare_opt.svg)

In this section, `opt` on Ice Lake is compared with `opt_avx` from Haswell, as requested.

### 1. BLAS

Ice Lake is only modestly faster than Haswell in the BLAS implementation:

- `1.46x` at `N=400`
- about parity around `N=800` to `N=1400`, with speedups between `0.93x` and `0.97x` when expressed as Haswell/Ice Lake runtime ratio

In practice this means the two machines are very close for BLAS at larger sizes, and Ice Lake is only clearly better at the smallest input. That suggests the BLAS library is already well-optimized on both systems and is limited less by raw ISA width than by memory movement and the library's own tuning choices. Since the benchmark pins to a single core, the larger socket-level core count does not matter here.

### 2. `neopt`

The literal unoptimized implementation improves only slightly on Ice Lake:

- `1.11x` at `N=400`
- `1.04x` at `N=1000`
- `1.04x` at `N=1400`

This is the behavior to expect from code that is dominated by poor memory access patterns and scalar loop nests. Ice Lake has a better memory hierarchy, but it cannot fundamentally rescue a version that repeatedly traverses large matrices with minimal reuse and no SIMD-aware structure.

### 3. `neopt_equiv`

The fair unoptimized baseline also improves only slightly:

- `1.16x` at `N=400`
- `1.05x` at `N=1000`
- `1.04x` at `N=1400`

Again, the architecture helps, but only at the margin. The distributive rewrite removes redundant work, yet the implementation is still scalar and still misses the locality and vectorization improvements that the optimized version exploits.

### 4. `opt`

The optimized version is where Ice Lake shows the clearest advantage:

- `1.66x` faster than Haswell at `N=400`
- `1.38x` at `N=600`
- `1.17x` at `N=1000`
- `1.23x` at `N=1400`

This is exactly where the Ice Lake features matter:

- AVX-512 doubles vector width over Haswell AVX2,
- the 48 KB L1 cache supports a larger block size (`40` instead of `32`),
- the 1.3 MB private L2 cache is much larger than Haswell's 256 KB L2, so blocked work can stay closer to the core longer,
- 64-byte alignment allows efficient aligned AVX-512 accesses.

At the same time, the gain is clearly much smaller than a theoretical `2x`, and that is also expected. Several factors limit the realized speedup:

- the algorithm still performs the same total memory traffic,
- not every part of the solver is vectorized,
- AVX-512 can trigger lower operating frequencies than narrower SIMD,
- scalar strip-handling and control code remain.

So the observed `~1.2x` to `~1.7x` advantage over Haswell is a realistic outcome: Ice Lake benefits materially from AVX-512 and the larger caches, but the full solver is not a pure compute-bound kernel.

## Speedup comparison between architectures

To make the cross-architecture effect more explicit, it is useful to compare the *internal* speedups of each platform:

- `neopt_equiv` relative to `neopt`
- `opt` relative to `neopt_equiv`
- `blas` relative to `opt`

Here I express speedup as a percentage improvement over the slower version:

```text
speedup_pct = (runtime_slower / runtime_faster - 1) * 100
```

- [Speedup comparison: Haswell vs Ice Lake](graphs/speedup_compare.svg)

Table:

| N | `neopt_equiv vs neopt` Haswell | `neopt_equiv vs neopt` Ice Lake | `opt vs neopt_equiv` Haswell | `opt vs neopt_equiv` Ice Lake | `blas vs opt` Haswell | `blas vs opt` Ice Lake |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 400 | 94.1% | 101.8% | 895.2% | 1331.9% | 149.1% | 118.9% |
| 600 | 99.5% | 98.3% | 870.1% | 1120.1% | 149.2% | 92.9% |
| 800 | 109.9% | 104.9% | 1055.1% | 1148.5% | 119.3% | 75.8% |
| 1000 | 104.7% | 106.3% | 965.8% | 1089.2% | 130.2% | 88.0% |
| 1200 | 104.8% | 107.0% | 935.7% | 1097.5% | 135.6% | 87.4% |
| 1400 | 106.3% | 107.0% | 907.8% | 1087.2% | 140.0% | 89.4% |

Three patterns stand out.

### 1. `neopt_equiv vs neopt` is almost architecture-independent

The percentage gain stays close to `~100%` on both machines. That is the expected result, because this improvement comes from regrouping the final symmetric matrix-vector phase and roughly halving the amount of work there. Since this is mostly an algorithm-structure effect, the relative gain is nearly the same on Haswell and Ice Lake.

### 2. `opt vs neopt_equiv` is stronger on Ice Lake

This is where Ice Lake clearly pulls ahead. The speedup grows from about `8.7x` to `11.6x` on Haswell (`870%` to `1055%`) to about `11.9x` to `14.3x` on Ice Lake (`1087%` to `1332%`). In other words, the optimized code benefits more from the newer machine than the scalar fair baseline does.

That matches the code and the hardware:

- AVX-512 doubles vector width relative to AVX2,
- the larger L1 supports `BLOCK_SIZE=40`,
- the much larger L2 helps blocked reuse,
- 64-byte alignment makes the wide vector loads/stores more effective.

### 3. `blas vs opt` is smaller on Ice Lake

The gap between BLAS and the hand-written optimized version shrinks on Ice Lake. On Haswell, BLAS is roughly `119%` to `149%` faster than `opt_avx`; on Ice Lake, the gap is only `76%` to `119%`.

This does **not** mean BLAS got worse. It means the custom optimized version improved more than BLAS when moving from Haswell to Ice Lake. That is consistent with the earlier architecture comparison: the naive versions barely improved, BLAS improved only modestly, but the AVX-enabled optimized version gained the most from the new vector width and larger caches.

## Conclusions

The Ice Lake analysis confirms the same overall hierarchy as on Haswell:

```text
BLAS < optimized < fair unoptimized < literal unoptimized
```

The optimized version benefits the most from the new architecture because it is the only one structured well enough to exploit it. The naive versions gain only a few percent over Haswell, while the optimized version gains roughly `17%` to `66%` depending on size.

The main architectural reasons are:

- AVX-512 provides wider vector execution,
- the larger L1 cache supports a larger tile,
- the much larger private L2 improves blocked reuse,
- 64-byte alignment is more valuable for 512-bit loads/stores.

The main limiting factor is that wider vectors do not remove the memory traffic or control overhead of the full algorithm, and AVX-512 can reduce turbo frequency. Because of that, Ice Lake delivers a clear but not dramatic speedup over the Haswell optimized implementation, while BLAS remains ahead of both hand-written versions.
